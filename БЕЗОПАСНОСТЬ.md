# Безопасность сайта «ДарЛес» — отчёт по аудиту

Дата проверки: 7 сентября 2026 г.
Проверялись: `index.html`, `catalog.html`, `product.html`, `admin.html` и все скрипты в `js/`.

Сайт статический (GitHub Pages), без сервера и базы данных — значит, классических
серверных уязвимостей (SQL-инъекции, взлом БД, утечка паролей пользователей) у него быть
не может. Основные риски здесь другие: XSS (выполнение чужого кода в браузере посетителя)
и защита токена GitHub в админ-панели. Именно по ним и шла работа.

---

## Что было найдено и исправлено

### 1. XSS через данные каталога — КРИТИЧНО, исправлено

**Было:** названия, подписи и описания растений вставлялись в страницу через `innerHTML`
без экранирования. Если бы в `products.js` попал текст с HTML-тегами (например, при копировании
описания с чужого сайта, или если бы кто-то получил доступ к репозиторию), в браузере
посетителя выполнился бы чужой код.

**Стало:** все данные проходят через функцию `esc()`. Пути к картинкам дополнительно
проверяются функцией `safeImg()` — принимаются только относительные пути внутри `images/`,
никаких `javascript:` и `data:`-ссылок. Внешние ссылки фильтруются `safeUrl()` — только `http(s)`.

Проверено автотестом: в каталог подставлялось растение с `<img src=x onerror=...>` и
`<script>` в названии, подписи и описании — ни одна инъекция не сработала ни на одной странице.

### 2. Выполнение кода из репозитория в админ-панели — КРИТИЧНО, исправлено

**Было:** админ-панель читала `js/products.js` с GitHub и разбирала его через `new Function()`,
то есть **исполняла как код**. Если бы в репозиторий попал вредоносный файл, он выполнился бы
прямо в открытой админке — там, где в этот момент находится токен GitHub с правом записи.

**Стало:** написан собственный разборщик, который читает файл как текст и вытаскивает поля
построчно, без `eval` и `new Function`. Проверено: все 13 растений разбираются корректно,
цикл «прочитать → записать → прочитать снова» даёт идентичный результат.

### 3. Токен GitHub хранился в localStorage — ВАЖНО, исправлено

**Было:** токен с правом записи в репозиторий сохранялся в `localStorage` навсегда. Он
оставался на диске после закрытия браузера, и его мог прочитать любой скрипт на странице.

**Стало:**
- токен больше **никогда** не пишется в `localStorage`; старые сохранённые токены при первом
  открытии панели автоматически удаляются;
- по умолчанию токен живёт только в памяти вкладки и стирается при её закрытии;
- появилась галочка «Запомнить токен до закрытия вкладки» (`sessionStorage`) — на выбор владельца;
- кнопка «Забыть токен» теперь надёжно чистит и память, и хранилище;
- в панели добавлена памятка по безопасной работе с токеном.

### 4. Content-Security-Policy — добавлена

На все четыре страницы добавлена политика безопасности контента. Она запрещает браузеру
загружать и выполнять что-либо постороннее, даже если инъекция всё-таки где-то проскочит:

| Правило | Что делает |
|---|---|
| `script-src 'self'` | выполняются только скрипты из этого репозитория, никакого встроенного JS |
| `object-src 'none'` | запрещены Flash/Java-объекты |
| `frame-ancestors 'none'` | сайт нельзя встроить в чужой iframe (защита от кликджекинга) |
| `base-uri 'self'` | нельзя подменить базовый адрес и увести все ссылки на чужой сервер |
| `form-action 'self'` | формы не могут отправить данные наружу |
| `connect-src` | сеть только к своему домену; в админке дополнительно к `api.github.com` |

Чтобы политика заработала, весь встроенный JavaScript вынесен из HTML в отдельные файлы:
`js/home.js`, `js/catalog-page.js`, `js/product-page.js`, `js/admin-page.js`.

### 5. Мелкие исправления безопасности

- Все ссылки `target="_blank"` получили `rel="noopener noreferrer"` — чужая страница
  больше не может управлять вкладкой вашего сайта и не видит, откуда пришёл посетитель.
- Добавлены `X-Content-Type-Options: nosniff` и политика `referrer`.
- Параметр `?id=` на странице растения проверяется как целое число — мусор в адресе
  просто показывает «Растение не найдено».
- Имя репозитория и ветки в админке валидируются перед запросом к GitHub — нельзя
  подставить произвольный адрес.
- Загружаемые фото ограничены 12 МБ и проверяются на тип, чтобы панель не зависала.
- `admin.html` закрыт от индексации: `noindex,nofollow` в мета-теге и `Disallow` в `robots.txt`.

## Что осталось по вашей части (организационное)

Технически защитить статический сайт полностью нельзя — часть безопасности зависит от вас:

1. **Админ-панель не защищена паролем и не может быть защищена** на статическом хостинге:
   любой, кто откроет `admin.html`, увидит форму. Но **без вашего токена GitHub он ничего
   не изменит** — панель просто не сможет писать в репозиторий. Токен и есть пароль.
2. **Храните токен как пароль.** Не пересылайте его в мессенджерах, не открывайте админку
   на чужом компьютере, после работы жмите «Забыть токен».
3. **Выдавайте токену минимальные права:** доступ только к репозиторию `lera-project`,
   разрешение только `Contents: Read and write`. Никогда не создавайте classic-токен со всеми правами.
4. **Ставьте токену срок жизни** (например, 90 дней) — если он утечёт, ущерб ограничен по времени.
5. **Включите двухфакторную аутентификацию** на аккаунте GitHub — это защищает сам репозиторий.
6. Если токен всё-таки засветился — немедленно удалите его на github.com в разделе
   Settings → Developer settings → Fine-grained tokens и создайте новый.

## Проверки, которые были прогнаны

- Все страницы открываются без ошибок JavaScript (проверено запуском в реальном движке браузера).
- XSS-тест с четырьмя видами инъекций на трёх страницах — ни одна не сработала.
- Разбор и пересборка каталога товаров — данные не теряются и не искажаются.
- Все внутренние ссылки и файлы отдаются с кодом 200.
